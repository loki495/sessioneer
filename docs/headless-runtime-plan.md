# Parallel tmux + headless runtimes — OpenCode and Codex implementation plan

Status: **Codex server-backed MVP implemented**, on `refactor/headless-runtime`
(2026-08-27). The remaining Codex parity work is bridge reconnect recovery
and persisted pending requests.
Phase 0 (live API verification) and Phase 1 (the runtime capability
contract) are done - see the Phase notes in "Phased plan" below. Replaces
the cancelled MCP-server idea (deleted). Andres's decision rule: a
headless runtime is added per-agent only where it genuinely makes sense;
the tmux path stays the universal baseline.

Codex planning was added 2026-08-26 from the protocol generated by the
installed `codex-cli 0.150.1` (`codex app-server generate-json-schema
--experimental`). Codex has a real headless embedding surface, so it should
use `codex app-server`, not a tmux TUI scrape. The app-server protocol is
versioned but currently marked experimental; pinning a tested minimum CLI
version and probing capabilities at startup are therefore part of the design.

## Decisions locked

- **Every capability Sessioneer exposes for a tmux session must also be doable
  from a headless session, per agent** — a "runtime" is a per-agent choice,
  not a global mode. If an agent has no usable headless session mode, it
  stays tmux-driven and we don't pretend otherwise.
- **opencode is the first headless runtime** (via `opencode serve`).
- **claude is excluded for now.** The Claude Agent SDK does not run on a
  Pro subscription without separate pay-per-API: the June-15, 2026 monthly
  Agent SDK subscription credit was cancelled ("The previously announced
  monthly credit... isn't available" - Anthropic support); the SDK is
  built around API-key/Claude-Platform auth (pay-as-you-go), and the
  subscription-replay workarounds are explicitly forbidden by the SDK's
  own terms. Not worth it under the no-pay-per-API constraint.
- **antigravity has no headless session mode** (only one-shot
  `agy -p`). Stays tmux-driven.
- **codex uses `codex app-server` as its primary runtime.** `codex exec
  --json` is a useful one-shot test/fallback surface, but it does not provide
  the persistent, bidirectional session ownership Sessioneer needs for approvals,
  questions, steering, and live updates.
- **`opencode serve` is a persistent host service, not a throwaway.** It
  runs as a systemd user unit (`opencode-serve.service`, port `4096`) and
  is expected to be up at all times — it's part of Sessioneer's own health check
  (`opencode_serve_check()` / the health box). Restart it only when a
  change actually needs reloading (a setting, the Sessioneer opencode plugin, or
  a hook it loads). Once it's up, we can spin up any number of sessions
  against it freely.
- **Codex needs two persistent host-native processes.** The Codex app-server
  is one; a small Sessioneer Codex bridge is the other. The bridge owns a long-lived
  app-server JSON-RPC connection and exposes a narrow Sessioneer-shaped Unix-socket
  API to the existing socket-activated PHP host agent. This is required
  because Codex sends approvals and `request_user_input` as JSON-RPC requests
  to the connected client, and their replies must carry the original request
  id. A one-request-one-process PHP connection cannot safely own that lifecycle.

## Why this framing (grounded in current code)

Sessioneer already abstracts most per-agent seams: `AgentAdapter` (spawn,
identity, hooks, permission vocab), `TranscriptRouter`,
`SessionStatusStore`, `PromptInteractionService`. What's missing is the
**runtime** dimension — whether a given agent session lives in a tmux
pane or behind a headless server. The tmux path is what all the
`TmuxService`/`SessionService`/hook code assumes; a headless path needs
to supply the *same* primitives from a different source.

## The abstraction: a per-agent runtime

Add a `runtime` notion so each agent declares which runtimes it supports,
and each runtime implements a **capability contract**:

| Capability | tmux runtime | headless runtime (v2 `/api/session` for opencode) |
|---|---|---|
| lifecycle create | spawn into a tmux pane via `AgentAdapter::build_spawn_argv()` | `POST /api/session` `{ location: { directory } }` |
| list / detail | `SessionService::list_all_sessions()` (tmux + sidecar) | `GET /api/session`, `GET /api/session/:id` |
| kill | `kill-session` | `DELETE /session/:id` |
| status working/idle/blocked | 5 hooks / agent plugin + pane capture | `GET /api/session/:id/event` SSE (session.status idle/busy/retry + deltas) + `GET /session/status` |
| send message | `PromptInteractionService::send_message()` (tmux keystrokes) | `POST /api/session/:id/prompt` `{ prompt: { text }, delivery: steer, resume }` |
| answer permission | `answer_prompt()` (tmux keystrokes) | `POST /api/session/:id/permission/:requestID/reply` `{ reply: once\|always\|reject }` |
| answer question | `answer_multi_question()` / `send_escape()` | `POST /api/session/:id/question/:requestID/reply` `{ answers: [[label…]] }` |
| abort | `send_escape()` | `POST /api/session/:id/interrupt` |
| read transcript | `TranscriptService` (JSONL) | `OpenCodeTranscriptService` (opencode.db — **unchanged**, already works) |
| todo / plan / quota | plan-file service | `GET /api/session/:id/todo` (todo); plan/quota backends unchanged |

The seam: a runtime provides the same shapes the tmux path produces, so
controllers/views stay runtime-agnostic. Where they can't match (e.g. a
tmux pane title, `tmux attach`), the headless path exposes what it has
and the view degrades gracefully.

Before adding Codex, change the registry key from just a generic
`RuntimeType::HEADLESS` implementation to an **(agent, runtime)** provider.
`RuntimeRegistry` already caches by that pair, but `build()` currently maps
every headless agent to `HeadlessRuntime`, which is OpenCode-specific. Rename
that class to `OpenCodeHeadlessRuntime` (or equivalent) and add a separate
`CodexHeadlessRuntime`; do not grow one class full of agent conditionals.

## Codex app-server capability mapping

The installed app-server protocol already covers the important Sessioneer surfaces:

| Sessioneer capability | Codex app-server v2 method/event |
|---|---|
| create | `thread/start` with `cwd`, model, sandbox and approval policy |
| list active / archived | `thread/list` with pagination and `archived` filter |
| detail + transcript | `thread/read` (`includeTurns`) or paged `thread/turns/list` / `thread/items/list` |
| resume / fork | `thread/resume` / `thread/fork` |
| archive / delete | `thread/archive` / `thread/delete` |
| send new message | `turn/start` with typed text/image/audio input |
| steer active turn | `turn/steer` with the required `expectedTurnId` precondition |
| interrupt | `turn/interrupt` with `threadId` + `turnId` |
| working / idle | `thread/status/changed`, `turn/started`, `turn/completed` |
| transcript deltas | `item/started`, item delta notifications, `item/completed`, agent-message deltas |
| command approval | server request `item/commandExecution/requestApproval` |
| file-change approval | server request `item/fileChange/requestApproval` |
| broader permission grant | server request `item/permissions/requestApproval` |
| question / form | server request `item/tool/requestUserInput` |
| context / quota | `thread/tokenUsage/updated`, `account/rateLimits/read`, `account/rateLimits/updated` |
| model / effort / plan mode | `model/list`; overrides on `turn/start`; collaboration mode `plan`/`default` |

This is materially better than TUI observation: status, complete tool data,
questions, transcript items, token usage, and approvals are structured and
identified. Hooks should be optional enrichment for Codex, not the source of
truth. Polling is still required as reconciliation after bridge restarts or a
missed event, but event ingestion should provide the normal low-latency path.

### Codex bridge state and I/O

- Run app-server on a host-only Unix socket. Do not expose its WebSocket
  listener to the LAN; the existing Sessioneer web container continues to see only
  the host-agent socket.
- The bridge initializes one app-server client connection, consumes all
  notifications/server requests, and reconnects with bounded backoff.
- Persist only normalized Sessioneer state in the existing SQLite stores: Codex
  thread id, active turn id, status, last event cursor/timestamp, pending
  request method/id/payload, token usage, and last error. Keep raw protocol
  payloads only where needed for diagnostics and cap their size.
- Host-agent actions call the bridge over a second private Unix socket. The
  bridge serializes JSON-RPC writes and correlates responses; answering a
  prompt revalidates that the same pending request is still current before it
  sends the response carrying the original JSON-RPC id.
- On reconnect, list/read threads and active status to repair cached state.
  Explicitly verify what happens to an unanswered server request when the
  owning connection drops; do not assume it can be answered from a new client.
- Use app-server history as the canonical transcript. A direct JSONL reader
  may be a recovery/import path, but must not become the live protocol when
  `thread/read` and paged turn/item APIs are available.

### Canonical Sessioneer prompt mapping for Codex

- Command and file-change decisions expose only decisions advertised by the
  request's `availableDecisions`/schema. Typical mappings are accept,
  accept-for-session, decline, and cancel; persistent exec/network amendments
  need explicit UI treatment rather than being silently collapsed to "always".
- `item/tool/requestUserInput` maps directly to Sessioneer's multi-question form,
  keyed by each question's stable `id`. Its response is an object of
  `{questionId: {answers: [...]}}`, not the positional OpenCode/Claude shape.
- Secret questions must never be persisted or included in push bodies/logs.
- A blocking request sets the session to `blocked`; resolving it returns to
  `working` unless a terminal turn event has already made the session idle.

## What "adjust the hooks and expectations accordingly" means concretely

This is the part Andres flagged, and it's where tmux and headless really
diverge:

- **Status source.** tmux/hook path: `SessionStatusStore` fed by the 5
  Claude hooks or the agent's plugin + pane capture. Headless opencode:
  `GET /api/session/:id/event` (SSE) — the `session.status` event
  (`idle`/`retry`/`busy`), plus text/reasoning/tool deltas and
  `session.idle`. Poll `GET /session/status` as a fallback. So headless
  status comes from the server, not the pane — no `capture-pane`. The
  `SessionStatusStore` contract stays; only the feeder changes.
- **Drive mechanism.** Permission + question answers become HTTP
  (`/api/session/:id/permission/:requestID/reply`,
  `/api/session/:id/question/:requestID/reply`), answered by id/label,
  not tmux keystroke sequences. `answer_multi_question` and `send_escape`
  have no headless meaning for opencode; `interrupt` replaces escape.
- **Expectation**: sessions are server-owned, not pane-owned. A headless
  session isn't `tmux attach`-able; the web UI becomes its only live view.
  No pane title/spinner detection — status is from the server/events.

## Multi-workdir (verified live)

The running serve already hosts sessions across directories: each session
carries a `directory`/`path`/`projectID`, and `/project` lists multiple
worktrees (incl. `~/www/sessioneer`). So **one
serve instance can manage sessions in many workdirs** — no per-project
serve needed.

**Confirmed live (2026-08-26):** `POST /api/session` with
`{ "location": { "directory": "/tmp/sessioneer-headless-probe" } }` created a
session at that directory (create+delete a throwaway; removed afterward,
sessions untouched). So arbitrary-workdir creation is clean via `location.directory` —
no workspace plumbing required. This was the last risk for Sessioneer's
"New Session arbitrary workdir" feature; it's resolved.

### Codex work

- **Codex Phase 0 — live protocol proof, no Sessioneer writes.** Start app-server
  on a temporary Unix socket with the existing logged-in Codex account;

  temp git repo; start a harmless read-only turn; observe event ordering;
  steer and interrupt it; archive/delete only the throwaway. Separately cause

  initialize/reconnect, framed JSON-RPC request correlation, normalized event

  capability probing, and health-box reporting. Fail soft when Codex is not

- **Codex Phase 3 — lifecycle and read-only UI.** Implement thread list,

- **Codex Phase 4 — drive and blocking UI.** Implement `turn/start`, steer,
  interrupt, command/file/permission approvals, and `request_user_input`.
  Every action re-reads the bridge's current thread/turn/pending-request state

  treat arbitrary uploaded files as text mentions/paths only after a live
  behavior check.
- **Codex Phase 5 — events, quota, and recovery.** Use notifications as the
  normal status/transcript source, account/thread usage notifications for the
  quota UI, and polling/list/read as reconciliation. Cover bridge restart,
  app-server restart/upgrade, duplicate events, late responses, resolved
  prompts, reconnect backoff, and a thread active in another Codex client.
- **Codex Phase 6 — parity and rollout.** Run the full feature matrix against
  Codex, document genuine non-equivalences, add Codex as a New Session choice,
  and keep the tmux implementation available only if it provides a tested
  recovery benefit. Do not make Codex globally required for Sessioneer startup.

## Tests (run against the live serve; sad path included per policy)

- **Use the real `opencode serve` service** — it's a persistent host
  service, expected to be running (that's the health-check requirement).
  If it's down, the tests fail/flag it rather than spawning a substitute.
  If a change under test needs reloading (a setting, plugin, or hook the
  server loads), restart `opencode-serve.service` first, as a normal
  op.
- Tests create and then **delete** their own throwaway sessions against
  it, in a temp workdir with a fixture/no-cost setup, and clean up — never
  touching Andres's real sessions. (Andres confirmed: any number of
  sessions may be spun up from the running serve.)
- Drive the runtime via `proc_open` + curl: `POST /session` (create),
  `GET /session/status`, `POST /session/:id/message`,
  `POST /session/:id/permissions/:permissionID` (allow + deny),
  `/question` + reply, `DELETE /session/:id`.
- Assert canonical shapes match what the tmux path produces (so
  controllers/views don't care).
- Sad path: bogus session id → handled `{ok:false,message}`/HTTP error,
  not a crash; answer on a resolved/orphaned permission → handled;
  permission answered without a live pending request → handled.
- No billable model calls in tests (fixture provider / dry run).

Codex tests need two tiers:

- A deterministic fake JSON-RPC app-server for unit/integration coverage of
  ordering, reconnect, duplicate notifications, server requests, stale prompt
  answers, malformed messages, and app-server/bridge unavailability. This is
  the default suite and must not authenticate or make model calls.
- An explicit live smoke test, skipped unless enabled, against the installed
  CLI on temporary sockets and a temporary repository. It creates only its own
  marked threads and cleans them up. Any turn that can consume quota must
  require an opt-in environment flag; ordinary `tests/run.sh` stays no-cost.

## Effort

Substantial but phased — this is the "longer-term re-architecture"
`todo:194` item, not a small self-contained feature. Phase 0-1 are cheap
(read-only research + the contract). Phases 2-4 are the real build and
should live on a `refactor/*` branch (the repo's convention for changes
big enough that the live site could break mid-way), then be merged and
deleted. Not a `master`-direct change.
